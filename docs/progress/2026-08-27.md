## AWS Lightsail deployment - real progress, one credential mixup left to resolve

Provisioned real AWS infrastructure: `container-service-1` (Lightsail Container Service, us-east-2) and `CriticalViewerDb-1` (Lightsail Managed Database, MySQL 8.4.11), with an app-scoped `criticalviewer_app` MySQL user (not the master user) for the running app to use.

Confirmed Lightsail Container Service only allows one publicly-reachable container per deployment, which doesn't fit this app's SPA-calls-a-separate-API shape directly - added a fourth container, `proxy` (nginx), as the sole public endpoint, routing `/api/*` to `backend-api` and everything else to `frontend-ui`. Side benefit: SPA and API now share one origin, so CORS isn't needed for real traffic.

Three real, separate infrastructure bugs found and fixed via actual Lightsail logs (not guesswork) getting the proxy working:

1. **Container names can't have underscores** on Lightsail - renamed `backend_api`/`frontend_ui` to `backend-api`/`frontend-ui` everywhere.
2. **`.LATEST` isn't a valid Lightsail image version token** - only real numeric versions; `containers.json.example` now documents checking `aws lightsail get-container-images` for the current number each time an image is repushed (no deploy script exists yet to automate this).
3. **Lightsail runs all containers in one deployment inside a shared network namespace** (pod-style), not per-container DNS like Docker Compose - nginx's `backend-api`/`frontend-ui` hostnames were never resolvable there at all, regardless of timing. Fixed by parameterizing the proxy's upstream targets via env vars (`BACKEND_API_UPSTREAM`/`FRONTEND_UI_UPSTREAM`) - `backend-api:8080`/`frontend-ui:5173` locally (Compose DNS), `localhost:8080`/`localhost:5173` on Lightsail - templated into `nginx/templates/default.conf.template` via the official nginx image's own envsubst entrypoint step. Combined with an earlier fix (lazy per-request DNS resolution via `resolver` + `set $var`, needed because Lightsail has no `depends_on` equivalent to sequence container startup) so nginx starts reliably regardless of which container comes up first.

**Result as of tonight**: the deployment reaches `ACTIVE` state, and the live public URL (`https://container-service-1.8w23bem0htgvm.us-east-2.cs.amazonlightsail.com/`) actually loads the real SPA - confirmed directly, not just via AWS status fields. The one remaining issue is a genuine credential mismatch: `POST /api/movies` (and presumably every DB-touching endpoint) fails with `Access denied for user 'criticalviewer_app'` - confirmed via direct `mysql` CLI test (bypassing the app entirely) that the password currently in `containers.json` doesn't match what's actually set on that MySQL user. Not a bug in the app or the proxy - just needs the password reset via `ALTER USER` (connecting as `dbmasteruser`, the account with admin rights - `criticalviewer_app` is a separate, more limited user created afterward specifically for the running app) and `containers.json` updated to match exactly, verified via direct `mysql` CLI *before* redeploying.
